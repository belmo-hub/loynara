Cloudflare Tunnel lets Railway web stay private and avoids that Railway edge surface without changing application architecture. This adds a small metered connector service. It does **not** prove Cloudflare has no URI telemetry; inspect actual Cloudflare/tunnel logs with synthetic tokens before accepting Gate 1. Do not enable request-path debug/Logpush fields. If a later verified redaction solution makes direct Railway ingress equally safe, that can be a separate reviewed simplification.

## Trusted ingress policy (local implementation; deployment verification pending)

Production requires `TRUSTED_INGRESS=cloudflare_tunnel`. The old `TRUST_PROXY_CLIENT_IP` must be absent or exactly `false`; other values fail startup. Unknown/blank ingress modes and production `local` mode fail startup. Local development and compiled synthetic previews retain the conservative local bucket with absent or `local` mode; their configuration guards reject tunnel mode. The declared production environment also refuses local fallback at request time.

Only `CF-Connecting-IP` supplies the visitor address. Strict single-address parsing rejects lists, ports, scoped IPv6 and malformed IPv4. Native IPv6 is canonicalized and masked to /64 before HMAC, matching Better Auth's default peer granularity. IPv4 remains address-specific with unchanged hashing; IPv4-mapped IPv6 is converted to IPv4 before masking and shares that exact IPv4 identity. Different native /64s remain independent. A purpose-separated HMAC under the existing server secret produces the peer identity; existing per-scope HMAC database keys and all programme/account/member/location limits remain. Addresses are not logged by this path. Better Auth explicitly uses the same Cloudflare header instead of its default forwarded-header list; its existing session IP storage and authentication limits remain, not a new analytics feature.

Every caller of `enforcePeerLimit` requires valid metadata in tunnel mode, including enrollment, card, recovery, merchant/staff and unsubscribe APIs. All auth GET/POST handlers validate ingress before Better Auth. Invalid metadata returns HTTP `503` with only `{"error":"Service unavailable"}` and `Cache-Control: no-store`, without consuming a global bucket. The internal `INVALID_INGRESS` error emits only `{"event":"invalid_ingress"}`, bounded to once per 60 seconds per process using monotonic time and one process-global timestamp (also shared across route-module loads). There is no request-keyed map, raw header/IP, URL, or credential in that event. Replicas/restarts each have their own allowance; this is a structured-log diagnostic, not proof of an alert delivery. Health may stay green during an ingress failure, so operators must inspect this event and functional monitoring. The Mailgun webhook retains its pre-auth peer resource bound plus signature/timestamp/event checks; an invalid ingress returns the existing retryable `503` without processing its body. Provider IP is transport metadata, never proof of Mailgun identity. `/api/health` remains a DB-backed, header-independent 200/503 readiness probe. Existing internal CLI worker/ops checks do not represent visitors and need no visitor IP. No general URL-based limiter exemption was added.

**All production processes/jobs:** set `TRUSTED_INGRESS=cloudflare_tunnel` in the applicable production environment before restarting/deploying web, `worker`, `production:ops-check`, `diagnose`, and the production migration job/configuration. They share the production guard even when a job does not handle HTTP. Do not remove the guard from jobs. No Railway variable was changed by this follow-up.

**Synthetic preview limitation:** absent/`local` mode deliberately ignores visitor headers. In a production-style synthetic build Better Auth can use its shared `no-trusted-ip` per-path bucket; tests/development may instead use its localhost fallback. This is accepted for the controlled preview, can couple synthetic users' auth limits, and is not visitor-isolation or production evidence. Preview networking and IP tracking are unchanged.

**Required before enabling this policy on the release origin:**

- Verify the web service has no generated Railway public domain, custom public domain, public TCP proxy or alternate externally reachable origin. Tunnel is the sole public ingress; PostgreSQL remains private. The setting is an operator assertion, not cryptographic authentication of headers.
- All services/administrators in the Railway environment are trusted: its private network is environment-wide, not a per-service authorization boundary. Review peers/credentials; no untrusted workload may reach the origin.
- Verify the dedicated connector targets only the intended private web listener. Audit Cloudflare Workers/subrequests and transforms; no unreviewed Worker may rewrite client metadata. Pseudo IPv4 must not overwrite headers, and visitor-IP-removal transforms must not remove the chosen field.
- Verify controlled IPv4/IPv6 traffic yields valid stable identities, distinct visitors have distinct keys, malformed/missing metadata fails closed, and direct public bypass is unavailable. Verify health probes still work without the header. Use bounded functional checks, not live limit exhaustion.
- Independently review this exact commit before setting production variables/deploying. These network/header checks are **NOT RUN** and remain a Gate-1 blocker. Do not infer verified ingress from Host, X-Forwarded-* or CF-Connecting-IP alone.

Official basis, reviewed 29 September 2026: [Cloudflare header behavior](https://developers.cloudflare.com/fundamentals/reference/http-headers/) (including Worker/Pseudo IPv4 caveats), [Tunnel outbound connections](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/), and [Railway private networking](https://docs.railway.com/networking/private-networking). The application design above is our policy, not a claim that these providers authenticate arbitrary origin headers.
