# Launch blockers — 2026-09-25

The repository is a local, synthetic-data build. **It has not been publicly deployed or used with real merchants or customers.** External expenditure during this run: **€0**. The draft €49/location/month (excluding any applicable VAT) is proposed merchant pricing, not an incurred charge or an approved tax position.

## Before any public browser-card pilot

1. **Operator identity and permission:** establish the business operator, the right to conduct this activity, invoicing/tax position, customer support contact and merchant contract. Code cannot approve business-operation or self-employment permission.
2. **Legal/data and recovery review:** replace the draft privacy/participation pages with operator-specific terms, lawful-basis/consent wording, processors, retention periods and cross-border details if Morocco is used. Card closure now removes optional contact/recovery details and local Apple device registrations/orphan push tokens and retires both identifiers, but the ledger, redemptions and consent history remain pseudonymous until an operator-approved retention schedule exists. There is no verified contact ownership or independent lost-link recovery; guests must save the private bearer card URL. Public enrollment therefore takes no email/marketing data. Merchant-account deletion and remote Wallet pass revocation also remain open.
3. **Production infrastructure:** provide a separate PostgreSQL deployment, approved HTTPS domain/reverse proxy, private secret storage, supervised web/worker services, access controls, encrypted offsite backups and restoration drills. Run migrations and a production-specific security review before traffic. The verified compiled **LOCAL PREVIEW** is isolated and loopback-only; it is not a production deployment. The local Docker database, Mailpit and demo credentials are forbidden for production startup.
4. **Destination security and operations:** PostgreSQL-backed limits and app-side sensitive-path log suppression are now in code; tenant/role checks were exercised through real HTTP sessions. At the approved proxy, overwrite and validate client-IP forwarding before enabling `TRUST_PROXY_CLIENT_IP`, and suppress/redact bearer card, Wallet token and Apple device-library-ID paths plus `api/qr?value=` query values in **proxy/access logs**. Review session/reset policy and any reverse-proxy uploads/error logging before public traffic. Schedule bounded expired-rate-counter pruning and monitor 429s. Add a real customer recovery flow only after ownership verification is designed and tested.
5. **Physical and accessibility verification:** clean install, compiled preview, worker replay, backup/isolated restoration, browser checks and dependency review were run locally. A Mac camera reading a phone-displayed QR, phone-to-phone HTTPS enrollment/scan, physical iPhone/Android behavior, and a screen-reader/keyboard checkout review remain **NOT RUN**. Browser camera emulation is not hardware evidence.

The current `npm audit --json` and `npm audit --omit=dev --json` each report **4 moderate** findings and no high/critical findings. The resolved path is the direct **development tooling** dependency `drizzle-kit@0.31.11` → `@esbuild-kit/esm-loader@2.6.5` → `@esbuild-kit/core-utils@3.3.2` → `esbuild@0.18.20`; the other resolved esbuild versions are 0.25.12 and 0.28.2. [GHSA-67mh-4wv8-2f99](https://github.com/evanw/esbuild/security/advisories/GHSA-67mh-4wv8-2f99) applies to esbuild's development server at ≤0.24.2; this app does not run that server, and both app listeners bind to loopback. The [Drizzle upstream issue](https://github.com/drizzle-team/drizzle-orm/issues/5304) confirms the transitive dependency remains in the toolchain. The audit suggests a major downgrade to 0.18.1, which was not applied without migration compatibility evidence. This remains an unresolved supply-chain finding, not a clean audit.

The browser-card journey can be piloted with wallet and live billing disabled after these gates and an explicit deployment destination approval. No wallet provider is required for the browser card.

## Additional gates for optional integrations

| Integration | Exact external prerequisite and remaining verification |
| --- | --- |
| Apple Wallet | Apple Developer Pass Type ID, matching pass certificate/private key and WWDR chain, stable web-service secret, public HTTPS URL, APNs reachability, Apple device. Install, register, award, push, fetch, redeem and QR scan on device. Test certificate expiry/rotation. |
| Google Wallet | Wallet issuer and authorized service account, enabled API, public HTTPS logo, designated demo test accounts then publishing approval, Android device. Save, update, scan and proximity behavior must be checked. Google controls nearby presentation. |
| External email | Approved sender/domain, customer email verification, consent and unsubscribe flow, suppression/quotas, delivery and bounce/complaint webhooks, reviewed campaign; explicit permission for a specific promotional send. Local Mailpit is a sink, not proof of deliverability. |
| Billing | Select payment provider per jurisdiction, obtain test account/keys, implement hosted checkout/portal, signed idempotent webhooks, tax/invoice treatment and cancellation/grace behavior. `manual_pending` is a draft state, not a subscription entitlement or live payment. |
| Morocco | Separate legal, data transfer, language and payment review. MAD configuration and French enrollment copy do not establish Moroccan launch readiness. |
