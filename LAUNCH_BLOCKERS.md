# Launch blockers — 2026-09-25

The repository is a local, synthetic-data build. **It has not been publicly deployed or used with real merchants or customers.** External expenditure during this run: **€0**. The draft €49/location/month (excluding any applicable VAT) is proposed merchant pricing, not an incurred charge or an approved tax position.

## Next protected device-test gate

The **separate** device-test database, restricted secrets, build-only compiled artifact and one-pass worker check are prepared locally. Its HTTPS origin and Access team/audience are deliberately unset, port 3002 is closed, and no tunnel or DNS route is active. Before any external change, the owner must approve one specific package: exact FQDN and Cloudflare account/zone, named testers and one-hour exact-email Allow policy, Cloudflare processing of synthetic traffic, Access app/Tunnel/DNS-route creation, origin JWT enforcement and proxy log policy, and the **confirmed incremental cost**. Cloudflare advertises a free small-team tier but [new Zero Trust setup asks for payment details](https://developers.cloudflare.com/cloudflare-one/setup/); without the owner's existing account/domain details, an exact cost cannot be asserted. The full phone journey remains **NOT RUN**.

Google Demo Mode is the first Wallet path if an authorized Android tester and issuer are available. The adapter now prepares a versioned per-program URL for a saved merchant PNG, but its image route is **disabled** in both protected previews and no public asset has been published. Google-supplied Save-button artwork, a **separately approved minimal provider-facing route**, issuer credentials, tester account and real Save/update test are still absent. Browser pages remain behind Access. Apple remains an alternative only with Apple-issued signing material, iPhone and separately approved callbacks. Neither provider is enabled in the device-test launcher.

## Before any public browser-card pilot

1. **Operator identity and permission:** establish the business operator, the right to conduct this activity, invoicing/tax position, customer support contact and merchant contract. Code cannot approve business-operation or self-employment permission.
2. **Legal/data and recovery review:** replace the draft privacy/participation pages with operator-specific terms, lawful-basis/consent wording, processors, retention periods and cross-border details if Morocco is used. Card closure removes optional contact data and local Apple device registrations/orphan push tokens and retires both identifiers, but ledger, redemptions and consent history remain pseudonymous until an operator-approved retention schedule exists. A synthetic `.test` email can be verified locally through Mailpit, but there is no independently verified lost-link recovery for real customers; guests must save the private bearer card URL. Public enrollment takes no email/marketing data. Merchant-account deletion and remote Wallet pass revocation remain open.
3. **Production infrastructure:** provide a separate PostgreSQL deployment, approved HTTPS domain/reverse proxy, private secret storage, supervised web/worker services, access controls, encrypted offsite backups and restoration drills. Run migrations and a production-specific security review before traffic. The verified compiled **LOCAL PREVIEW** is isolated and loopback-only; it is not a production deployment. The local Docker database, Mailpit and demo credentials are forbidden for production startup.
4. **Destination security and operations:** PostgreSQL-backed limits and app-side sensitive-path log suppression are now in code; tenant/role checks were exercised through real HTTP sessions. At the approved proxy, overwrite and validate client-IP forwarding before enabling `TRUST_PROXY_CLIENT_IP`, and suppress/redact bearer card, Wallet token and Apple device-library-ID paths plus `api/qr?value=` query values in **proxy/access logs**. Review session/reset policy and any reverse-proxy uploads/error logging before public traffic. Schedule bounded expired-rate-counter pruning and monitor 429s. Add a real customer recovery flow only after ownership verification is designed and tested.
5. **Physical and accessibility verification:** clean install, compiled preview, worker replay, backup/isolated restoration, browser checks and dependency review were run locally. A Mac camera reading a phone-displayed QR, phone-to-phone HTTPS enrollment/scan, physical iPhone/Android behavior, and a screen-reader/keyboard checkout review remain **NOT RUN**. Browser camera emulation is not hardware evidence.

The current `npm audit --json` and `npm audit --omit=dev --json` each report **4 moderate** findings and no high/critical findings. The resolved path is the direct **development tooling** dependency `drizzle-kit@0.31.11` → `@esbuild-kit/esm-loader@2.6.5` → `@esbuild-kit/core-utils@3.3.2` → `esbuild@0.18.20`; the other resolved esbuild versions are 0.25.12 and 0.28.2. [GHSA-67mh-4wv8-2f99](https://github.com/evanw/esbuild/security/advisories/GHSA-67mh-4wv8-2f99) applies to esbuild's development server at ≤0.24.2; this app does not run that server, and both app listeners bind to loopback. The [Drizzle upstream issue](https://github.com/drizzle-team/drizzle-orm/issues/5304) confirms the transitive dependency remains in the toolchain. The audit suggests a major downgrade to 0.18.1, which was not applied without migration compatibility evidence. This remains an unresolved supply-chain finding, not a clean audit.

The browser-card journey can be piloted with wallet and live billing disabled after these gates and an explicit deployment destination approval. No wallet provider is required for the browser card.

## Product work still open

The remaining product gaps are physical-device verification and scale/abuse review of the new offline award queue, per-location subscription lifecycle and provider handoff, full French merchant flow, append-only staff/revocation audit history, provider messaging and remote pass invalidation, real-contact recovery, neutral review requests, and broader retention/deletion administration. Offline events stored in one browser's localStorage are not a backup; clearing that browser before reconciliation can lose pending events. The current adviser is explicitly rule-based; its tested model-provider contract does not make a live AI integration. Multi-location, purchase rounding, referrals and local synthetic campaigns/automations are implemented but still need real merchant/device acceptance and scale review. The merchant-named HTML print sign and scoped JSON download flow are locally verified, but a sign needs a separately approved HTTPS URL before it can serve phones at a counter. At checkout, the largest remaining customer interaction is finding the saved private card link; there is no independently verified recovery or live Wallet path if it is lost. Do not advertise unfinished features as available.
