# Security audit, 15 October 2026

Independent review of the whole Loynara application: Next.js web app, worker, operator scripts, deployment files, the Cloudflare/Railway setup as far as it can be seen read-only, and the ticket loop script. Base: `railway-rc` at `680266d` (the code production runs). Fixes are on branch `security/audit-2026-10-15`; nothing was merged or deployed.

## How it was tested

- Isolated local stack: PostgreSQL 18 in container `loynara-security-pg` on 127.0.0.1:54397 (tmpfs, synthetic data only), app on 127.0.0.1:3081, both `next dev` and a compiled `next start` build. No test touched production data.
- Production was only read: plain GET/HEAD requests to public pages, DNS lookups, and one refused read-only Railway API query.
- Every finding below has a reproduction: a request, a test, or a file location. Items that could not be proven are listed separately under "Not proven".
- The HTTP probes are in `security/probes/` and refuse any address but loopback. Run them against `npm run dev` with `PUBLIC_REGISTRATION_ENABLED=true`, for example `BASE=http://localhost:3000 node security/probes/probe-tenancy.mjs`. Locally all visitors share one address bucket, so clear `rate_limits` in the local database between runs. `probe-auth.mjs` covers cross-origin and auth endpoints, `probe-paths.mjs` sign-in path variants, and `probe-headers.mjs` headers on signed-in pages.
- Secrets were never printed. Where a secret file was found, only its path is given.

## Findings

### H-1. Production credentials in the iCloud-synced Desktop checkout

**What.** The main checkout at `~/Desktop/Loynara` keeps live credentials in its ignored `var/` folder. The Desktop folder is synced to iCloud Drive (`~/Library/Mobile Documents/com~apple~CloudDocs/Desktop` links to it), so these files are copied to iCloud and every device signed in to that Apple account.

Files (paths only, values not read):

- `var/cloudflared-production.token`: the production tunnel token
- `var/railway-production-auth.secret`, `var/railway-stage-a.env`: Railway access
- `var/r2-stage-a-backup.env`: backup bucket credentials
- `var/healthchecks-stage-a.env`
- `var/cloudflared-device-test.token`, `var/integrated-preview-nfc-20261005/preview-connector.token`, `var/device-test.env`, `var/preview.env`
- `var/demo-access.json`, `var/device-test-access.json`, `var/preview-access.json`
- `.env`, `.env.local`

Outside the repository, `~/Loynara-operator-keys/` still holds `credential.json`, `owner.json`, `cashier.json` and `transport-private.pem`. Your earlier note already says to delete these.

**Reproduce.** `ls -la ~/Desktop/Loynara/var` and `ls -la ~/Library/Mobile\ Documents/com~apple~CloudDocs/ | grep Desktop`.

**Impact.** Whoever gets into the iCloud account, or any synced device, gets these credentials. The tunnel token is the most serious one. With it, someone can run their own connector for the production tunnel. Cloudflare then sends part of the `app.getloynara.com` traffic to that connector, which sees card links, session cookies and staff passwords in clear text. The Railway and R2 credentials give access to the deployment and to the encrypted backups.

**Fix (your decision, production change).**

1. Move the secret files out of `~/Desktop` into a folder that is not synced, for example `~/Developer/Loynara-secrets` (mode 0700), or into the macOS keychain or a password manager. Delete the operator key files you no longer need.
2. Rotate whatever may already have been synced: the production tunnel token (create a new connector token in Cloudflare and update the Railway `cloudflared` service), the Railway token, and the R2 access keys. The device-test and preview tokens can simply be revoked if those tunnels are retired.
3. Optional: turn off "Desktop & Documents Folders" in iCloud settings, or move all Loynara work under `~/Developer` as you already do for worktrees.

**Status.** Needs your decision. Nothing was moved or rotated.

### H-2. The ticket loop lets ticket text run code on the Mac

**What.** `scripts/ticket-cycle.py` pastes a ticket's title and description into the prompt of `IMPLEMENT_CMD`. Your configured command (`~/.config/loynara-loop/config.env`) allows `Bash(npx *)`, `Bash(npm run *)`, `Write` and `Edit`. That combination can run any code: `npx` runs any package from npm, and `Write` plus `npm run` can run any script. The command also inherited the caller's full environment. When a run made no change, the last 25 lines of the command's output were posted to the ticket as a comment, and the review output was posted to the pull request.

**Reproduce.** Read `scripts/ticket-cycle.py` at `680266d`: `process()` builds the prompt from `issue_text()`, `env = dict(os.environ, ...)`, and the "no change" branch comments `log_tail`. The redaction patterns would not catch a Cloudflare tunnel token (base64 JSON). The loop is not scheduled today (`launchctl print gui/$UID/com.loynara.ticket-loop` reports not loaded), so nothing has run.

**Impact.** Anyone who can write or edit a ticket's text in LOY, or any integration with tracker write access, can instruct the command to read local files, including the credentials in H-1, and print them. The script then posts them to the ticket. A branch could also change CI or package install scripts.

**Fix (on branch).**

- New required setting `ALLOWED_AUTHORS`. A ticket is only picked up when its reporter and every author of its summary and description (from the tracker's activity history) are on the list. If the list is empty, nothing runs. Other tickets get a short comment and the `needs-founder` tag.
- The command's output stays in the local log. Nothing it prints is posted to the tracker. The review is saved locally and only posted to the pull request with `POST_REVIEW=1`.
- A branch that touches any top-level dot-folder (`.github/` and tool settings), `scripts/ticket-*`, any `package.json` or `package-lock.json`, `.npmrc`, `Dockerfile*` or `.dockerignore` is kept locally and not pushed.
- Both commands now get only `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_ALL`, `TMPDIR` and `TERM` from the environment, plus their own variables.
- `check` fails without `ALLOWED_AUTHORS` and warns when `IMPLEMENT_CMD` grants arbitrary code execution.
- Regression tests: `scripts/ticket-cycle.test.ts` (5 tests).

**Still your call.** Set `ALLOWED_AUTHORS` to your login before using the loop again. Consider dropping `Bash(npx *)` from the implementation command. As long as the command can run `npm run`, the author list is the real protection. Keep H-1's secrets off any machine the loop runs on.

### M-1. No per-account limit on failed sign-ins

**What.** Sign-in was limited only per visitor address: 30 per 15 minutes in the app, plus Better Auth's own short per-address limit in production. Neither limit counts attempts against a single account.

**Reproduce.** `src/app/api/auth/sign-in-account-limit.integration.test.ts` sends wrong passwords for one account, each from a different `CF-Connecting-IP`, through the real route in tunnel mode. On the original route, all attempts return 401 and the correct password still works. A fourth test sends 30 wrong guesses at the same moment. The fix as first written still had all 30 passwords checked, because it read the counter first and recorded failures only afterwards; the final fix lets at most 10 through. All four tests fail before the fix and pass with it.

**Impact.** Password guessing against a known owner or cashier email address, spread across many addresses (cheap with rented proxies), was not slowed at all. The minimum password length of 12 helps, but operator-chosen or reused passwords remain at risk.

**Fix (on branch).** `src/app/api/auth/[...all]/route.ts` limits sign-ins per lowercased email in the existing PostgreSQL limiter. The key is HMAC-hashed, so no raw email is stored. Every attempt atomically reserves a slot before the password is checked, so parallel guesses cannot slip past the count. The slot is given back unless the password was wrong (`refundRateLimit` in `src/lib/rate-limit.ts`). After 10 failures in 15 minutes, every sign-in for that account, including one with the correct password, gets `429 RATE_LIMIT` with `Retry-After`. Successful sign-ins do not count. A sign-in body the limiter cannot read (not JSON, or no email string) is refused with 400, so it cannot bypass the limit. Verified on the compiled build: after 10 failures, the correct password returned 429 with Retry-After 828 seconds. Trailing-slash and double-slash path variants are redirected by Next.js (308) before the route runs, so they do not bypass either.

**Lock notice.** When an account is locked, its own address gets an email. For a staff account, every active owner of the merchant gets one too, naming the staff address and pointing to Team to revoke access. At most one round of notices goes out per account per day, however often the lock is triggered. Accounts without an active merchant role and unknown addresses get none. The queued job holds user ids only; addresses are read at send time, and a recipient who has lost owner access by then is skipped. Code: `src/lib/sign-in-lock-notice.ts`, delivered by the worker as job kind `email.signin_lock`. Tests: `src/lib/sign-in-lock-notice.integration.test.ts`. Not exercised: a real send through Mailgun or Mailpit; the message goes through the same `sendTransactional` path as the recovery mails.

**Trade-off (kept strict, decided 15 October).** Someone who knows a staff email can keep that account locked by sending 10 wrong passwords every 15 minutes. That is the usual cost of an account lock, and it was kept on purpose. A lock only blocks new sign-ins; devices already signed in stay signed in for up to 7 days, so a counter phone keeps working. A successful guess on an owner account would expose customer data, card reissue and staff invites. The lock notice shows whether lockouts happen and who is affected. If they do become a problem, the gentler variant counts per account and address (about 10) plus a higher per-account total (about 50).

### M-2. Production runs Next.js 16.3.6 with known advisories

**What.** `npm audit` lists six advisories against `next@16.3.6`, all fixed in 16.3.8: GHSA-cjq9-62q9-8jv4, GHSA-4jqv-mc3x-m676, GHSA-mcj8-r9mp-w47p, GHSA-f87g-xv8r-7p7x, GHSA-3w37-wq28-93x7 and GHSA-39w2-rjm5-chcv. It also flags `sharp@0.35.4` (librsvg memory bug, GHSA-wq5f-xc86-pv6w) and `source-map-js@1.2.1` (GHSA-68fv-2mgg-jv7q). The ticket LOY-199 note about four moderate findings is out of date: the full audit showed 4 moderate and 8 high.

**Applicability, checked against the code.** None of the Next.js server advisories applies to the current configuration. There is no `images.remotePatterns`, no Pages Router, no root catch-all route, no metadata image routes, and neither `use cache` nor Draft Mode is used. The development-server one (GHSA-39w2) does affect any `next dev` you run on the Mac: a malicious website you visit can read source snippets and logs from it. `sharp` only processes local images here, and SVG optimisation is off.

**Fix (on branch).** `next` and `eslint-config-next` pinned to 16.3.8, `sharp` 0.35.5, `source-map-js` 1.2.2. The production-only audit is now back to the 4 known moderate findings (drizzle-kit → esbuild 0.18, development tooling). What remains in the full audit is `braces` via `eslint-config-next` (lint-time only; npm's suggested fix is a downgrade to 14.x, so it was not applied). The build passes on 16.3.8.

**Status.** Fixed on the branch. Production picks it up with the next web deploy, which is your decision.

### M-3. A programme's enrollment budget can be exhausted

**What.** `POST /api/enroll` has two limits: 25 per visitor address per 15 minutes, and 300 per programme slug per hour. The programme limit is shared by everyone, and the join URL with the slug is printed on the counter sign.

**Reproduce.** A temporary integration test (not committed) against the real route in tunnel mode created cards for one programme from 13 different `CF-Connecting-IP` addresses, 25 each. The next request from a fresh address, a real guest, received 429. The steps: create a merchant, then loop `POST /api/enroll {slug, acceptedTerms:true}` 320 times with `cf-connecting-ip: 203.0.113.<1..13>`, then enroll once from `198.51.100.77`.

**Impact.** With 13 addresses an attacker can block new guests at one shop for an hour, repeatably. The junk cards also count towards the 10,000 open cards per location plan limit, which could be filled in about 34 hours at that rate.

**Decision and change (15 October).** The per-programme cap is raised from 300 to 500 new cards per hour, which is 20 addresses' worth of the per-address limit (20 × 25). Busy shops get more headroom, and blocking a shop now takes at least 20 addresses instead of 13. Test: `src/app/api/enroll/programme-join-limit.integration.test.ts` (500 joins from 20 addresses succeed, the next is refused; fails on 300, passes on 500). The cap is per programme, and each location has its own programme, so every branch of a multi-location merchant has its own budget.

**What this does not solve.** Twenty addresses are still cheap to rent, so a determined attacker can still block one shop for an hour, and junk cards still count towards the 10,000-card plan limit. Remaining options: (a) a Cloudflare rate-limit rule on `/api/enroll` (free plan: one rule, no code); (b) a challenge such as Cloudflare Turnstile on the join page (needs a CSP change); (c) a cleanup job that closes cards that never had a visit after N days. Separately, guests on a shop's own Wi-Fi share one public address, so at most 25 of them can join per 15 minutes through it. That is fine for normal days but could pinch at a launch event in a big shop; raise the per-address limit if that becomes real.

### M-4. No DMARC record

**What.** `dig TXT _dmarc.getloynara.com` and `_dmarc.mail.getloynara.com` return nothing. `mail.getloynara.com` has SPF (`include:mailgun.org ~all`) and the root has SPF with `~all`.

**Impact.** Mail claiming to come from `getloynara.com` (for example a fake "recover your card" mail) is not rejected by receivers, and you get no reports about it. Recovery mail is exactly the kind of message worth faking.

**Fix (DNS change, your decision).** Publish `_dmarc.getloynara.com TXT "v=DMARC1; p=none; rua=mailto:<reports address>"`, watch the reports for two weeks, then move to `p=quarantine` and later `p=reject`. Check that Mailgun signs with DKIM aligned to `mail.getloynara.com` first. Adding a CAA record that allows only the certificate authorities Cloudflare uses is a small related hardening step.

### L-1. Session token readable by page JavaScript

**What.** The session cookie is `HttpOnly`, but Better Auth also returns the session token in JSON: in the sign-in response body (`"token": ...`), in `/api/auth/get-session` and in `/api/auth/list-sessions`. Verified locally.

**Impact.** Only matters if a cross-site scripting bug ever appears. The CSP allows inline scripts, so the CSP would not stop such a script from reading the token and replaying it. No XSS was found in this audit: React escapes output, there is no `dangerouslySetInnerHTML`, and the generated HTML sign escapes its fields.

**Fix (your decision).** Either accept it (common for Better Auth apps), or block the token field in responses with a Better Auth `after` hook, which needs care with the client library. Moving to a nonce-based CSP would remove `'unsafe-inline'`, but every page would then render dynamically, as the comment in `next.config.ts` explains.

### L-2. Logged-in write routes without per-user limits

**What.** These routes have no rate limit: `cashier/award`, `cashier/redeem`, `transactions/reverse`, `staff/invite`, `staff/invite/revoke`, `staff/accept`, `staff/revoke`, `merchant/onboard`, `merchant/program/update`, `merchant/program/rewards`, `merchant/export`, `merchant/email/test`, `cashier/tap/pending`, `cashier/push/config`. Found by grepping every route for `enforcePeerLimit`/`enforceRateLimit`.

**Impact.** Small. All need a valid staff session and are bounded by role limits, for example a cashier awards at most 10 stamps per award. A compromised or careless cashier account could still book many awards quickly. The owner sees them in the activity list and can correct them.

**Recommendation.** Add a per-user limit to award and redeem (for example 120 per 15 minutes, matching lookup) and to staff invite/accept. Not changed here, because the right numbers are a product decision for busy counters.

### L-3. Runtime Docker image

**What.** `Dockerfile` copies the whole build stage (`/app`, including source, tests, docs, e2e, devDependencies) into the runtime image with `--chown=node:node`. The base image is referenced by tag, not by digest.

**Impact.** No direct exploit. If the app process were ever compromised, it could rewrite its own code, and the image ships more than it needs.

**Recommendation.** Copy only `.next`, `public`, `package*.json`, production `node_modules`, `scripts/` and `src/` (the start and worker scripts run from source via `tsx`). Keep the files owned by root and readable by `node`. Pin `node:26-bookworm-slim@sha256:...`. Needs a careful test of `npm start`, the worker and `production:migrate` before deploying.

### L-4. `X-Powered-By: Next.js` in production

**Reproduce.** `curl -sI https://app.getloynara.com/login | grep -i x-powered-by`.

**Fix (on branch).** `poweredByHeader: false` in `next.config.ts`, with a test in `src/security-headers.test.ts`. Verified on the compiled build.

### Info

- **I-1. One secret, many purposes.** Better Auth sessions, customer session cookies, rate-limit keys, email verification and recovery tokens, and (as a fallback) unsubscribe links all derive from `BETTER_AUTH_SECRET`, each with its own label. That is sound, but rotating the secret logs everyone out and breaks all outstanding links at once. Set a separate `PROMOTIONAL_UNSUBSCRIBE_SECRET` in production if it is not already set.
- **I-2. Invitation links are credentials.** Whoever holds an invite link can create the invited account (with invite sign-up on) and accept it, because staff email addresses are not verified. That is by design. Send invite links over a private channel. They expire after 7 days and can be revoked.
- **I-3. Card links and scan codes are bearer credentials** (already documented). Card tokens have 256 bits and scan codes 192 bits, so they cannot be guessed. They do appear in URL paths (`/card/<token>`) and in the `/api/qr?value=` query, so Cloudflare and browser history can see them.
- **I-4. HTTPS.** Every hostname now answers plain HTTP with a 301 to HTTPS, including `app.`, `mail-events.`, `unsubscribe.`, `preview.` and the root. The earlier note that "Always Use HTTPS" was off is out of date. HSTS is sent for a year with `includeSubDomains`, without preload.
- **I-5. Production ingress trust.** In production every per-address limit trusts `CF-Connecting-IP`. That is only safe if the Railway web service has no public Railway domain or TCP proxy. The Railway API refused a read-only domain listing with this token, so please confirm in the Railway dashboard (web service, Settings, Networking) that there is no public domain. The code side (strict parsing, fail closed when the header is missing) was reviewed and is fine.
- **I-6. Remaining dev-only advisories.** `drizzle-kit` → `@esbuild-kit` → `esbuild@0.18.20` (moderate, dev server only, not used) and `braces` via `eslint-config-next` (high, lint-time ReDoS). Neither runs in production.

## Not proven (hardening ideas, no exploit shown)

- `POST /api/card/<token>/contact` sends a fixed-template verification mail to any address the card holder types: at most 4 per address per hour, 10 per card and 30 per visitor address. Cards are free, so someone could use it to send unwanted verification mails, which hurts the sending domain's reputation. Not tested against Mailgun. Consider a daily cap per destination and per programme.
- `requestCardRecovery` returns faster when no verified card matches the email, so timing could reveal whether an address has a card. Not measured. If it matters, queue the work for both cases.
- The NFC SUN design allows a phone that taps a tag to keep the URL and use it later from elsewhere (counter-based replay protection still works). Staff confirmation, the only mode allowed in production, makes this harmless.

## What held up

- **Tenant and role separation.** 61 checks (57 refusals, 4 allowed actions) through real HTTP sessions on the local stack, covering two merchants, owner, manager, cashier, revoked staff and anonymous users. Every attempt was refused: cross-merchant lookup by scan code and by card number, award, redeem, correction, customer detail and list, retention, reissue, location select and a forged location cookie, rewards, brand, campaigns, automations, referrals, wallet readiness, tap policy, staff invite and revoke, programme update. Cashiers could not reach owner or manager functions or exceed the 10-stamp limit. Revoked staff were refused everywhere, including onboarding a new merchant and accepting another merchant's invite. Script: `security/probes/probe-tenancy.mjs`.
- **CSRF.** Better Auth refuses writes with a foreign, missing or `null` Origin (update-user, change-password, sign-in), and every app write route checks Origin. A `text/plain` cross-site POST is refused.
- **Auth surface.** Password reset, email change, account deletion, magic link and anonymous sign-in are all off. Callback URLs on auth routes are validated (no open redirect). The auth error page does not reflect input. The operator reset script revokes sessions and never prints passwords.
- **Webhooks and tokens.** Mailgun signature (HMAC, constant-time compare, 15-minute window, event de-duplication). Billing fixture signature, and the fixture is off in production. Apple pass token (HMAC per serial, constant-time compare). Unsubscribe token (AES-256-GCM). Customer session cookies (HMAC, 90-day idle and 365-day absolute lifetime). Invite tokens (256 bits, stored hashed).
- **NFC.** Counter-based replay protection, UID binding, tag status checks and staff confirmation in production.
- **Headers.** CSP without `unsafe-eval`, HSTS, nosniff, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer` on public and signed-in pages (`/merchant`, `/cashier`, `/merchant/staff`, `/merchant/customers` checked on the compiled build).
- **Injection.** No raw SQL built from input; `pool.query` calls use parameters. No HTML sinks. Outbound mail is plain text. Child processes use `execFile`/`spawn` with argument arrays.
- **Logging.** Runtime logs carry error names and job ids only, and Next.js request logging is off.
- **Secrets in git.** `gitleaks` over all 570 commits found 26 hits, all test fixtures (for example `sk_live_0123…`). No private keys, provider keys or tokens are committed.
- **Dependencies.** The lockfile resolves only from the npm registry with integrity hashes. Install scripts are limited to esbuild, fsevents and unrs-resolver.
- **Deployment files.** The runtime image runs as `node`, `.dockerignore` excludes `.env*`, `var/`, keys and dumps, CI uses `contents: read` and pinned action SHAs, and the repository is private.
