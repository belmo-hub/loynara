# Customer data access and assisted requests

This procedure implements the owner-approved 15 October 2026 identity/export policy in code and synthetic tests. Production activation and actual requests require the authorized operator. Never attach customer data or credentials to source control or public tickets.

The card offers two clearly labelled downloads. **Card activity** is the existing limited pseudonymous format and excludes contact records. **Personal data** includes all retained records attributable to that card in one read-only repeatable-read snapshot, with metadata explaining purposes, recipients, retention and exclusions. It never includes another card sharing an address, a referral counterparty, card/scan credentials, authentication or challenge hashes, device secrets or staff identifiers. Historic verification target addresses are withheld from self-service because they may have been entered without ownership proof; challenge dates/outcomes remain included, and assisted review can assess the separate address scope.

A contactless card uses its current private card credential. If the card has a stored verified email, a new one-use link sent to that address authorizes exactly that card for ten minutes. The link stays in a URL fragment, is removed from browser history by the confirmation page and is submitted only through a same-origin POST. Changing the contact or card credential, closure, expiry or prior consumption invalidates it. The export proof is consumed before generation; a failed or interrupted request requires a new proof. No marketing consent is inferred.

An unverified address is not identity proof. The self-service flow discloses neither that address nor contact-rich history. A missing private link, unverified address, closed card, unusually large record or unavailable email transport uses the assisted procedure:

1. The requester contacts the merchant/controller's privacy contact in its participation/privacy notice. The application also links `/datenschutz`; operator-specific contact details must be maintained there before launch. Do not ask the requester to send a private card URL, QR, password or full identity document by ordinary email.
2. The assigned Privacy Lead opens a restricted case with a random receipt, received date, scope and applicable response deadline. Aim to complete within seven days; track the separate legal response clock. A valid access request is not rejected solely because self-service credentials are unavailable.
3. The controller assesses identity proportionately using its established relationship and a safe communication channel. Record the method/outcome, not unnecessary copies of identity documents. A typed email, locator, photograph or scan code alone does not authorize disclosure. If proof is insufficient, explain what proportionate additional evidence is needed without confirming stored addresses or other cards.
4. An authorized custodian gathers only this subject/card's retained data using approved read-only tooling and a consistent snapshot. Review retained holds, closure/deletion receipts and processor-held records separately. Distinguish data no longer retained from data withheld to protect another person or a credential. Do not restore erased data or revive retired credentials to answer a request. This assisted review remains a human operator procedure; there is no public UUID-based export bypass.
5. The Privacy Lead checks completeness against the personal-export categories, redacts credentials and unrelated subjects, and includes purposes, recipients/categories, retention periods, request/complaint route and specific exceptions. For exceptionally large exports, arrange a complete bounded transfer; never substitute a silently truncated file.
6. Deliver through the verified private channel approved in the case. Record delivery/outcome and apply the approved case/evidence retention policy. Do not save a permanent public download link or copy export content into logs.

Automatic export generation reads cursor batches of 128 rows. Only after all categories and the database transaction succeed does the request receive an attachment. On the supported Linux/macOS host, staging opens a private mode-0600 file in a mode-0700 temporary directory, then immediately unlinks the file and removes its directory. Generation and transfer use only the open descriptor, bounded to 128 MiB and 256 KiB per record, with at most two active transfers per process and a 120-second cleanup deadline. A budget failure explicitly selects assisted access. The 120-second internal deadline and caller abort both cancel production and destroy a checked-out PostgreSQL connection, forcing half-open queries to stop. Checkout has a separate five-second bound and discards late acquisitions. A production slot remains reserved until the producer actually stops; it cannot hide a still-running query behind completed file cleanup. Successful completion, cancellation, generation failure and request abort remove private staging; no durable downloadable copy or second URL is created. There is no named staging copy during generation or transfer; abrupt process exit closes the descriptor and releases its storage. File creation or unlink failure fails the request with cleanup. Unlinking is not a claim of forensic secure erasure. Infrastructure must use private ephemeral storage and prevent backup/indexing of temporary storage.

The operator must verify actual email/provider delivery and contact routes before activation. Synthetic sender tests are not proof of real delivery or of a completed real access request.
